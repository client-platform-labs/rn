# 中国区分发与动态更新合规边界

- 研究日期：2026-08-18
- 适用范围：中国大陆生产发行；iOS App Store；华为、小米、OPPO、vivo、荣耀、腾讯应用宝、360 手机助手等 Android 渠道；纯 React Native 与 Brownfield
- 研究目标：为 React Native 灰度、离线包、热更新、远程开关和回滚划出可执行边界
- 结论性质：工程与合规研究，不构成法律意见；凡标为“需法务/渠道确认”的事项，不应由平台自动推断为合规

## 结论摘要

1. **“只更新 JS/Hermes/静态资源”不是天然合规豁免。** React Native JS 与 Hermes bytecode 都是可执行代码。Apple 2.5.2 禁止下载、安装或执行会引入或改变 App 功能的代码；2.3.1 又要求新功能、功能变化和产品变化对审核明确、可审。华为公开审核规则也禁止从其他来源执行会修改、替换或更新应用特性或功能的代码；360 的公开收录标准更直接写明“应用不能存在热更新行为”。因此，中国生产环境的可执行 OTA 应默认关闭，按 **App × OS × 分发渠道 × 变更类型** 单独放行，不能做成全公司默认能力。[A1][H1][Q1]
2. **中国监管并未公开规定“一切热更新均禁止”，但明确禁止用热更新/热切换擅自改变主要功能、申请权限、个人信息收集使用场景和范围。** 工信部同时要求分发平台持续巡查并对这类 App 停止服务；这使“未经商店复审改变受审状态”成为跨 Android 渠道的硬风险边界。[R3]
3. **动态加载本身处于监管视野内。** 《移动互联网应用程序信息服务管理规定》把“动态加载”列入应用程序分发服务的定义，并要求分发平台审核上架和更新版本、持续管理在架 App。企业自建 OTA 控制面是否因此构成该规定下的“分发平台”，需由法务结合服务对象、运营方式和主体关系判断，平台不能自行下结论。[R4]
4. **原生代码、原生 SDK、Manifest/entitlement、系统权限声明、签名、隐私清单和商店元数据变化必须走商店版本。** Android 覆盖更新还受 application ID、签名证书/有效轮换证明和 versionCode 约束；iOS/Android 的“原生回滚”通常要发布一个更高版本号的前向修复包，不能把商店版本直接降回旧包。[A3][D1][D2][D3]
5. **隐私变化是独立于“代码是否原生”的阻断条件。** 只要 OTA、远程配置或 SDK 配置改变个人信息处理目的、方式、种类、权限、接收方、跨境流向或调用频率，就必须先完成隐私影响判断、披露更新及所需同意；工信部还要求 SDK 使用前评估、集中展示并及时更新 SDK 信息。2026 年监管通报继续集中检查 SDK 未完整列明、非必要权限和声明与实际不一致。[R3][R5][R6][R7][R11]
6. **APP 备案、许可和安全评估不是一次性“上架材料”。** 境内提供互联网信息服务的 App 原则上应备案；备案信息变化要办理变更。新闻、出版、教育、影视、宗教等还可能有前置审批；游戏、图书杂志、宗教、新闻在中国大陆 App Store 有 Apple 明示的额外材料要求。通过 OTA 打开新的业务类别、舆论/社会动员功能或算法推荐能力，可能触发备案变更、许可、安全评估或算法备案，必须人工判定。[R1][R2][R4][R8][R9][A4]
7. **最稳妥的平台策略是三条发布通道，而不是一个“万能 OTA”：**
   - 商店通道：原生代码、可执行逻辑和高风险功能变化；
   - 受限内容通道：不执行、且不改变主要功能/权限/个人信息处理/许可状态的静态内容与资源；
   - 例外 OTA 通道：默认禁用，仅在法务、隐私、安全、产品和目标渠道共同批准后，对明确 App/渠道/变更类别限时开放。

## 一、证据等级与术语

### 1. 证据等级

- **确定规则**：现行法律、行政法规、部门规章/规范性文件或 Apple/渠道当前公开规则有直接文字依据。
- **渠道差异**：渠道公开规则的约束强度或发布能力不同；只对该渠道作结论。
- **需法务/渠道确认**：规则需结合业务事实解释，或本轮未取得足够清晰的公开一手规则。此类事项在平台中应表现为 `BLOCKED_PENDING_APPROVAL`，而不是“默认合规”。
- **建议性基线**：安全工程措施或 GB/T 推荐性标准，可作为公司控制，但不能伪装成法定结论。

### 2. 本文术语

- **商店包更新**：经 Apple 或 Android 渠道审核并分发的新 IPA/APK/App Bundle。
- **可执行 OTA**：安装后从企业服务端下载并由 App 执行的 RN JS、Hermes bytecode、脚本、插件或其他可改变行为的代码。
- **离线包**：可在弱网/离线运行的资源集合。是否合规取决于其内容是否可执行、是否改变功能，而不取决于名称是否叫“离线包”。
- **远程开关/热切换**：不一定下载新代码，但通过服务端配置改变功能、流程、权限触发、数据处理或内容。
- **静态内容**：图片、文案、字体、媒体或纯数据；若其中包含脚本、表达式、模板解释器输入、路由/动作 DSL，仍可能构成可执行或功能性载荷。
- **回滚**：既包括 OTA Bundle 回退，也包括商店原生版本回退；二者规则完全不同。

## 二、中国大陆共同监管底线

### 1. APP 备案、主体核验与业务许可

**确定规则**

- 《反电信网络诈骗法》第二十三条要求设立移动互联网应用程序按国家规定办理许可或备案；提供封装、分发服务的一方应登记、核验开发运营者真实身份并核验 App 功能、用途。[R1]
- 工信部信管〔2023〕105 号明确：在境内从事互联网信息服务的 App 主办者应履行备案，未备案不得从事 App 互联网信息服务；分发平台、网络接入服务提供者和终端生产企业不得为未备案 App 提供分发、接入或预置。App 应在显著位置标明备案编号并链接备案系统；信息变更或注销时应办理相应手续。[R2]
- “APP 备案/服务备案号”不等同于“经营性 ICP 许可证”。是否还需增值电信业务经营许可或行业许可，要根据业务性质判断，不能只检查一个备案号即放行。[R2][R4]
- 《移动互联网应用程序信息服务管理规定》第七条要求：新闻信息服务须有互联网新闻信息服务许可；其他依法需要主管部门同意或许可的服务，取得后方可提供。第十四条要求具有舆论属性或社会动员能力的新技术、新应用、新功能按规定安全评估。[R4]

**对动态发布的约束**

- OTA/远程开关若改变 App 名称、包名/Bundle ID、签名指纹、域名、服务类型、前置审批项、运营主体或备案登记的其他信息，应先走备案变更判断；平台只能比对字段，不能判断许可充分性。[R2][X3]
- 动态打开新闻、出版、教育、影视、宗教、游戏、金融、医疗、地图、网约车、社交/UGC 等能力，不得仅凭“代码已在壳内”自动放行。应先进入行业许可和备案人工审批。

**需法务确认**

- 某 App 是否属于“在境内从事互联网信息服务”、是否属于纯单机例外；
- 具体业务需要非经营性备案、经营许可还是其他行业许可；
- 功能变化是否达到备案“信息发生变更”的程度；
- 企业自建 OTA 服务是否属于《移动互联网应用程序信息服务管理规定》中的应用程序分发服务。

### 2. 热更新、热切换与在架巡查

**确定规则**

- 工信部信管函〔2023〕26 号要求分发平台加强动态巡查。对公示信息不真实，或以“热更新、热切换”等方式擅自改变 App 主要功能、申请权限、个人信息收集使用场景和范围的违规 App，应停止提供服务。[R3]
- 同一通知要求终端加强对静默下载、热更新的监测，防止未经用户同意的私自启动、下载、安装；要求分发平台登记主要功能、权限及用途、个人信息处理规则，并保留审核日志。[R3]
- 《网络数据安全管理条例》第四十一条要求应用分发平台建立核验规则、开展网络数据安全核验，对不符合法律、行政法规或强制性国家标准的 App 采取警示、不予分发、暂停或终止分发。[R6]
- 《移动互联网应用程序信息服务管理规定》把“动态加载”纳入应用程序分发服务，并要求平台审核申请上架和更新的 App，持续处置数据安全、违法收集个人信息等问题。[R4]

**边界解释**

- 规则针对的是**改变后的实际功能和行为**，不是更新文件的扩展名。把 JS 改名为 JSON、把 Hermes bytecode 称为“资源”、把功能切换称为“配置”，不会改变风险性质。
- 预先在 Manifest 声明大量权限、再通过 OTA/配置逐步开启，并不能规避“擅自改变申请权限、个人信息场景和范围”的约束，反而会增加过度索权与声明不一致风险。[R3][R7]
- 服务端内容更新通常不等于 App 热更新，但若服务端内容动态切换了主要功能、审核时不可见的业务、付费模式、违法内容或数据处理行为，仍落入审核规避和信息不一致风险。

### 3. 个人信息、权限与 SDK

**确定规则**

- 《个人信息保护法》第六条要求目的明确、直接相关、影响最小、范围最小；第十四条规定，基于同意处理时，处理目的、方式或个人信息种类变化，应重新取得同意；第十七条要求事前显著、清晰、完整告知。[R5]
- 向其他个人信息处理者提供个人信息，原则上要告知接收方、目的、方式和种类并取得单独同意；敏感个人信息须有特定目的、充分必要性、严格保护措施，通常需单独同意并告知必要性和影响；相应高风险处理还应事前进行个人信息保护影响评估并留存记录。[R5]
- 《网络数据安全管理条例》第二十二条进一步要求：基于同意处理时，不得超出同意的目的、方式、种类和保存期限；处理目的、方式、种类变化应重新取得同意。第二十一条要求个人信息规则集中、易访问，并用清单列明收集及向其他处理者提供信息的情况。[R6]
- 工信部信管函〔2023〕26 号要求 App 使用 SDK 前评估其个人信息保护能力，通过合同明确责任，集中展示并及时更新 SDK 名称、功能和处理规则；SDK 自身应公开名称、开发者、版本、主要功能、使用说明和个人信息处理规则。[R3]
- 四部门《App 违法违规收集使用个人信息行为认定方法》把以下情形列为监管认定参考：未逐一列明嵌入第三方代码/插件的目的、方式、范围；变化后未通知；同意前采集；超授权采集；未经同意通过 SDK 向第三方提供；新增功能超出原同意范围却影响旧功能使用等。[R7]
- 2026 年中央网信办、工信部、公安部专项行动及 4 月、6 月通报继续检查：声明与实际不一致、SDK 未完整准确列明、非必要权限、超最低必要频率和无有效注销功能。[R11]

**Apple 的叠加要求**

- Apple 5.1.1 要求 App 内和 App Store Connect 提供隐私政策，说明 App 及第三方 SDK 的数据收集、使用、留存/删除和撤回方式；App Privacy 答案必须包含第三方伙伴并持续保持准确。[A1][A5]
- 自 2024-05-01 起，Apple 对所列第三方 SDK、Required Reason API、隐私清单和二进制 SDK 签名实施提交要求。此要求发生在商店包层面，OTA 不能修改原生 SDK、补交隐私清单或改变已申报 API reason。[A6]

**平台结论**

- 任一发布只要使 `data-inventory`、`sdk-inventory`、权限调用、处理目的/方式/种类、接收方、保存期限、跨境目的地或同意流程发生变化，自动发布必须停止。
- “只是修 Bug”不是隐私豁免。Bug 修复若会开始发送此前未发送的数据、修复某 SDK 初始化、提高采集频率或启用已有权限，仍是个人信息处理变化。

### 4. 数据跨境

**确定规则**

- 《个人信息保护法》第三十八、三十九条规定向境外提供个人信息的机制、告知与单独同意要求；《网络数据安全管理条例》和《促进和规范数据跨境流动规定》进一步规定安全评估、标准合同/认证和豁免情形。[R5][R6][R10]
- 2024 年《促进和规范数据跨境流动规定》对非关基运营者按重要数据、敏感个人信息和人数设置不同路径，也规定若干合同履行、人力资源、紧急情况及少量非敏感个人信息等豁免；豁免并不消除《个人信息保护法》下其他告知、合法性与安全义务。[R10]

**对交付平台的含义**

- OTA CDN、更新检测、崩溃监控、设备分群、SDK 遥测和控制面日志都可能产生个人信息或设备标识跨境；“Bundle 文件托管在境外”与“向境外发送用户/设备数据”应分开建模。
- 数据是否属于个人信息、敏感个人信息、重要数据，主体是否为关基运营者，以及应走何种出境机制，必须由法务/数据合规人员确认，平台不可仅凭数量自动作法律结论。

### 5. 签名、制品和版本连续性

**确定的技术规则**

- Android 系统覆盖更新要求 application ID 相同，签名证书相同或存在有效 proof-of-rotation；不同证书通常会被视为另一个 App。Android 以 versionCode 判断新旧并防止安装较低版本，渠道通常还要求新提交版本号递增。[D1][D2][D3]
- versionCode 是系统与渠道判断升级顺序的整数，应跨渠道全局单调递增；versionName 是面向用户的展示字符串，不参与 Android 系统的新旧判断，但必须与提交材料、更新说明和安装后展示保持一致。[D2][N1]
- 小米公开文档明确所有 App 应签名，并解释 v1/v2/v3 与证书轮换；更新包 versionCode 应高于在架版本。[X4]
- OPPO 提供签名变更申请流程，说明签名变更不是普通自动操作；荣耀通过证书指纹校验真实性，官方更新 SDK 将用户带到荣耀应用市场更新。[O3][N2]
- 工信部对电子签名认证的措辞是“鼓励/推动”，不能据此宣称所有 App 或 OTA Bundle 都有法定电子签名强制要求。[R3]

**公司应采用的安全基线**

- OTA 清单和载荷必须由独立发布密钥签名，客户端固定信任根并验证哈希、签名、App ID、原生壳版本、RN/Hermes 版本、能力包版本、发布时间和撤销状态。
- OTA 签名是供应链安全措施，不是 Apple/渠道审核豁免，也不是合规证明。
- Android 多渠道应使用可证明一致的签名策略和单调递增的全局 versionCode；如渠道代签或支持密钥托管，应单独维护签名谱系，禁止平台猜测可互相覆盖。

### 6. 现行、即将实施与草案必须分开

- 2025 年修正的《网络安全法》已于 2026-01-01 施行；现行文本进一步与《个人信息保护法》等衔接。[R12]
- 《个人信息保护合规审计管理办法》已于 2025-05-01 施行；处理超过 1000 万人个人信息的处理者至少每两年审计一次，处理 100 万人以上个人信息的处理者应指定个人信息保护负责人负责合规审计工作。用户规模及计算口径仍应由法务确认。[R13]
- GB/T 43739-2024、GB/T 43435-2023、GB/T 42884-2023、GB/T 45574-2025 等为现行推荐性国家标准，可用于公司治理、敏感个人信息和应用商店审核基线，但不能直接描述为强制性法律。[S1][S2][S3][S5]
- GB/T 47469-2026 已发布但截至研究日尚未实施，实施日期为 2026-11-01；应加入政策观察与提前适配，不应在 2026-08-18 写成已经生效。它的适用对象是**移动智能终端提供者**，用于指导终端个人信息保护功能设计、开发，覆盖权限细粒度授权、敏感行为提示与记录、设备标识访问、存储空间、自启动/关联启动和卸载等终端侧管理能力；它不会替代面向应用商店的 GB/T 43739-2024 或面向 App 生命周期的 GB/T 42884-2023。[S1][S3][S4]
- GB/T 47469-2026 的管理措施分为基本级、增强级，这是终端保护能力的分级，不能解读成按某个 App 的用户量自动定级，也没有为“高敏感 App”另设可执行 OTA 规则。处理敏感个人信息或大规模个人信息的 App 仍分别适用《个人信息保护法》《网络数据安全管理条例》及合规审计规则；例如《网络数据安全管理条例》第二十八条对处理 1000 万人以上个人信息的处理者叠加部分重要数据处理者义务，合规审计办法则使用 100 万人负责人、超过 1000 万人至少每两年审计的阈值。这里的对象、人数统计和义务叠加方式应由法务确认，不能和 GB/T 47469 的能力分级混为一谈。[R5][R6][R13][S4]
- 对交付平台的直接影响是兼容性而非新的“上架许可证”：应在 2026-11-01 前验证 OTA/远程开关不会绕开终端权限目的说明、单次/使用期间授权、权限自动重置、敏感调用标识和记录、自启动/关联启动控制；不能依赖静默后台权限或不可变设备标识维持灰度身份。[S4]
- 《互联网应用程序个人信息收集使用规定》截至研究日仍是 2026-01-10 发布的**征求意见稿**，没有正式施行日期；其结构化清单、SDK 管理和规则变化通知要求可作为前瞻设计输入，但不能作为现行硬法源。[R14]

## 三、Apple 中国大陆边界

### 1. 动态代码与远程功能

**确定规则**

- Apple 2.5.2：App 应自包含，不得下载、安装或执行会引入或改变 App 特性或功能的代码；教育类可编辑源码场景存在窄例外。[A1]
- Apple 2.3.1：不得包含隐藏、休眠或未记录的功能；所有新功能、功能变化和产品变化须在 App Store Connect 审核备注中具体描述，并可供审核。[A1]
- Apple 4.7 允许特定的 HTML5/JavaScript 小程序、小游戏、流媒体游戏、聊天机器人和插件模式，但附带软件索引、内容治理、隐私、原生 API、逐项权限同意及年龄限制等条件。这是一个需要按 4.7 设计并接受审核的产品模型，不是普通 RN OTA 的通用豁免。[A1]

**工程结论**

- RN JS、Hermes bytecode、脚本化 DSL 均按“可执行载荷”处理；平台不得因为没有 `.dylib`/原生机器码就自动判为 Apple 合规。
- 能否将某个纯 Bug 修复认定为没有“引入或改变特性或功能”，公开规则没有给出 RN 专用安全港。应由 App 所有人、法务和 Apple 审核沟通共同承担判断，不得由静态 diff 自动给出“Apple compliant”。
- 远程开关若开启审核时不可见、不可访问或未说明的新功能，触及 2.3.1；即使不下载代码，也不能默认放行。
- 如产品实质上是小程序/插件容器，应按 4.7 单独立项，不能把普通业务 Bundle 包装成“离线包”规避。

### 2. 中国大陆可用性与许可材料

- Apple App Store Connect 要求适用的中国大陆 App 提供并验证与工信部信息匹配的 ICP Filing Number；缺失或不匹配会使 App 无法在中国大陆提供。Apple 原文使用 “some apps/if applicable”，因此纯离线 App 等边界仍以工信部备案适用性和 App Store Connect 的实际状态为准。[A4]
- Apple 明示：游戏需 NPPA 批准号；图书/杂志内容需互联网出版许可；宗教内容需互联网宗教信息服务许可；新闻内容需互联网新闻信息服务许可，并需提交支持文件。[A4]
- 通过 OTA 增加上述内容或改变经营模式，不能假设原有 App Store 可用性材料仍然覆盖。

### 3. 隐私与 SDK

- App Privacy 回答必须覆盖 App 和第三方伙伴的实际数据处理，并在实践变化时及时更新；虽然隐私回答可不提交新二进制而更新，但这不等于动态代码变化已获 Apple 审核许可。[A5]
- 原生 SDK、Required Reason API、隐私清单和 SDK 二进制签名属于商店构建资产，必须走新商店包。[A6]

### 4. 灰度与回滚

- App Store phased release 在 7 天内按 1%、2%、5%、10%、20%、50%、100% 向开启自动更新的随机用户分发；可暂停，但用户仍可主动下载最新版本。它是**已审核原生版本的商店灰度**，不是 OTA 授权。[A2]
- Apple 明确不支持把 App Store 当前版本回退为以前版本；出问题时要创建并提交新版本。可暂停阶段发布、移除销售或让有问题的兼容版本停止下载，但已安装用户不会被自动降级。[A3]
- 因此 iOS 原生事故预案必须是“暂停扩散 + 服务端降级/熔断 + 更高版本前向修复”，不能承诺即时原生回滚。

### 5. 企业分发不是消费者 OTA 逃生口

- Apple Developer Enterprise Program 仅用于符合条件组织向其员工私下分发自研内部专有 App，并强调标准 App Store、Custom Apps、Ad Hoc 或 TestFlight 能覆盖的场景不应使用企业计划。不得把企业签名当作面向消费者绕过审核的渠道。[A7]

## 四、中国 Android 渠道差异

### 1. 跨渠道共同基线

- 所有面向境内互联网信息服务的渠道仍受 APP 备案、主体核验、在架巡查、个人信息和 SDK 规则约束。[R1][R2][R3][R4][R6]
- Android 系统允许不同安装器在签名、application ID 和版本条件满足时更新同一 App；这意味着多商店版本号和签名必须统一治理，否则会发生跨渠道覆盖、无法升级或签名分叉。[D3]
- App 内自行下载 APK/请求安装不是安全的统一方案。华为明确要求通过应用市场取得可执行更新组件，360 禁止未经确认的自动下载安装/自升级；荣耀则公开提供应用市场更新 SDK/自更新查询，并对部分老机型提到可按需通过安装器更新，体现了渠道差异。中国生产包仍应默认禁用 APK 自更新和 `REQUEST_INSTALL_PACKAGES`，仅在目标渠道公开规则或书面批准明确覆盖具体方案、且签名/版本/隐私门禁通过时例外审批；荣耀文档不是 RN 可执行 OTA 的授权。[H1][Q3][N2][N4]

### 3. 渠道矩阵的设计含义

- 不能用“Android 允许动态加载”替代渠道政策。Android OS 技术可行性、国家监管和商店合同是三层独立约束。
- 同一安装包若同时投放华为、360 等渠道，最低共同边界接近“禁用可执行 OTA”。若业务希望在其他渠道启用，必须使用可审计的渠道构建配置和服务端渠道鉴别，证明不会向禁用渠道下发。
- 渠道鉴别不得只信任可伪造的客户端字符串；至少将商店签名/安装来源、构建渠道、App ID 和服务端登记绑定。无法可靠识别时按最严格策略处理。
- 渠道公开规则会变化。平台需保存“规则版本、抓取/复核日期、法务审批单、渠道工单/合同附件”，并设置定期复核；不能把本文永久硬编码为法律真相。

## 六、可转成机器门禁的规则

以下门禁是**公司风险控制**。它们可自动发现明确不允许的情形，但通过门禁不等于取得法律或商店合规保证。

### A. 应用与渠道基线

1. `CN-DIST-001 TargetMatrixPresent`
   - 每次发布必须声明 App、OS、应用形态、目标渠道、国家/地区、安装来源、当前商店版本和规则快照版本。
   - 任一目标渠道规则状态为 `unknown`、过期或尚未完成合同复核，禁止可执行 OTA。
2. `CN-DIST-002 ChannelPolicyIntersection`
   - 计算所有目标渠道规则交集。
   - 包含 360 时 `executable_ota=false`；包含华为时禁止外部代码修改/替换/更新功能；包含 iOS 时应用 Apple 2.3.1/2.5.2。
3. `CN-DIST-003 NoSelfInstaller`
   - 生产商店包扫描 APK/IPA 下载、自安装、未知来源安装引导、`REQUEST_INSTALL_PACKAGES` 及第三方安装器调用。
   - 默认阻断，只有目标渠道书面批准的例外策略可解除。

### B. 备案、许可和元数据

4. `CN-FILING-001 ActiveFiling`
   - 发布前验证备案号存在、主体、App 名称、包名/Bundle ID、签名指纹和域名与登记台账一致。
   - App 内必须可见备案号并可跳转工信部备案系统。
5. `CN-FILING-002 FilingDiff`
   - 比较本次变更与备案字段；任一字段变化进入法务/备案负责人审批，禁止自动发布。
6. `CN-LICENSE-001 RegulatedFeatureDiff`
   - 维护受监管能力标签：新闻、出版、教育、影视、宗教、游戏、金融、医疗、地图/出行、直播、UGC/社交、算法推荐等。
   - 新增或实质变化一律要求许可证/备案/安全评估审批记录，不根据代码关键词自动判定“无需许可”。
7. `CN-METADATA-001 ReviewedStateMatch`
   - 对比商店描述、截图、年龄分级、付费模式、主要功能、隐私标签与发布后状态。
   - 任一重大不一致阻断远程开启。

### C. 制品与兼容性

8. `CN-ARTIFACT-001 ArtifactClassifier`
   - 检测 Mach-O/ELF/DEX、Framework/AAR、原生库、JS、Hermes bytecode、WebAssembly、脚本、表达式/动作 DSL。
   - 无法证明为非执行数据时，按可执行载荷处理。
9. `CN-NATIVE-001 NativeDiffZero`
   - OTA 不得改变原生代码、Manifest/entitlement、权限声明、原生 SDK、隐私清单、签名或商店元数据。
10. `CN-COMPAT-001 ExactCompatibility`
    - Bundle 必须匹配可机读兼容矩阵：App ID、平台、原生壳、RN、Hermes bytecode 版本、Runtime SDK、能力包和协议版本。
11. `CN-SIGN-001 StorePackageContinuity`
    - Android 更新必须检查 application ID、签名证书/轮换谱系和全局单调递增 versionCode。
12. `CN-INTEGRITY-001 OtaSignature`
    - OTA manifest 与每个文件必须验签、校验哈希、有效期和撤销状态；不允许 `fail-open`。
13. `CN-SBOM-001 DependencyDiff`
    - 生成原生与 JS 依赖 SBOM；任何新增/升级 SDK、远端脚本域、动态依赖均触发安全和隐私复审。

### D. 功能、权限与隐私

14. `CN-FUNCTION-001 MainFunctionInvariant`
    - 发布声明必须列出变更前后业务功能、路由、付费入口、内容类别和远程开关。
    - 自动策略只能证明“没有声明的变化”；是否属于“主要功能”仍需人工负责。
15. `CN-PERM-001 PermissionInvariant`
    - OTA/配置不得新增权限请求时机、用途、频率，不能把已有但未使用权限切换为使用。
16. `CN-PRIVACY-001 DataInventoryDiff`
    - 对比数据类型、目的、方式、必要性、敏感性、频率、保存期限、接收方、处理地点、跨境目的地和用户权利路径。
    - 任一变化阻断自动发布并进入隐私审批。
17. `CN-SDK-001 SdkBehaviorMatch`
    - SDK 名称、包名、版本、功能、权限、上报字段、端点、隐私政策和初始化时机必须与台账及 App 披露一致。
    - 同意前初始化或网络访问、声明外端点/字段、远程打开采集均阻断。
18. `CN-CONSENT-001 ConsentVersion`
    - 若审批判断需重新同意，必须先发布新的告知/同意版本，并验证拒绝路径不影响原有基本功能；不得把“同意新规则”作为静默更新前提。
19. `CN-XBORDER-001 DataDestinationDiff`
    - 出现新境外端点、境外接收方或数据类别时直接进入数据出境人工审批；机器只报告事实，不选择法律路径。

### E. 灰度、熔断与回滚

20. `CN-ROLLOUT-001 ApprovedCohort`
    - 灰度只能在批准的 App/渠道/版本内，按稳定随机或明确测试名单分群；不得按敏感个人信息或歧视性条件分群。
    - 远程功能灰度仍需通过功能/隐私门禁，不能借“1% 用户”降低合规级别。
21. `CN-KILLSWITCH-001 NonExpansiveKillSwitch`
    - 紧急开关只能关闭、降级或回到已经批准的行为，不能在事故中开启新权限、新采集或新业务。
22. `CN-ROLLBACK-001 RollbackEligibility`
    - OTA 仅可回滚到当前证书有效、未撤销、与现壳兼容、当前隐私/许可仍覆盖的 Bundle。
    - 原生回滚计划必须生成更高 versionCode/build 的前向修复任务，不能下发低版本包。
23. `CN-AUDIT-001 ImmutableReleaseRecord`
    - 保存审批人、规则快照、源提交、构建环境、SBOM、签名、哈希、目标用户、灰度变化、下载/激活结果、熔断和回滚记录。
    - 日志保存期限由公司制度与适用规则确定，不在平台内臆造统一法定年限。

## 七、必须人工审批的规则

### 1. 产品负责人

- 判断是否改变主要功能、业务模式、付费、年龄分级、内容类别或商店描述；
- 确认远程开关在审核时是否已披露且可访问；
- 确认灰度和回滚不会让不同用户长期处于不可解释的产品状态。

### 2. 隐私负责人

- 审查个人信息台账、SDK 行为、权限调用、同意/撤回、敏感个人信息和个人信息保护影响评估；
- 判断是否需更新隐私政策、App Privacy、SDK 清单及重新取得同意；
- 确认旧 Bundle 回滚后不会恢复已撤回或已废止的数据处理。

### 3. 安全负责人

- 审查载荷签名、密钥托管、供应链、下载域、TLS、反回放、兼容矩阵、漏洞修复与应急方案；
- 判断紧急修复是否可走受限 OTA，或必须使用商店加急/前向修复。

### 4. 法务/合规

- 判断 APP 备案、经营许可、行业许可、算法备案、新技术新应用安全评估和数据出境路径；
- 对 Apple 2.5.2、4.7、各 Android 渠道“主要功能/热更新”条款作事实适配；
- 确认征求意见稿和即将实施标准仅作前瞻输入，未被误当成现行法。

### 5. 渠道运营

- 在华为、vivo、荣耀、应用宝等后台或工单取得当前规则与书面答复；
- 负责商店分阶段发布、暂停、撤销、下架和版本回退等人工动作；
- 每次规则变化更新渠道快照和平台策略版本。

## 八、平台绝不能承诺自动化的事项

平台不得对业务方承诺：

1. “纯 JS/Hermes 更新一定不需要 Apple/Android 商店审核”；
2. “通过机器门禁即代表满足中国法律、备案、许可或 Apple 审核”；
3. “所有中国 Android 渠道都允许热更新、灰度或自更新 APK”；
4. “已有 APP 备案自动覆盖任何新增业务或功能”；
5. “隐私政策已更新就当然取得了有效同意或单独同意”；
6. “低于某个人数就当然无需任何数据出境义务”；
7. “签名过的 OTA Bundle 就得到 Apple、监管机构或应用商店认可”；
8. “原生版本可以在所有渠道即时回滚”；
9. “紧急安全修复天然豁免审核、个人信息和许可要求”；
10. “历史上审核通过的做法会被未来版本继续接受”。

## 九、推荐的中国生产发布策略

### 1. 三通道模型

**Store Lane**

- 承载所有原生变化、SDK 变化、权限/entitlement、可执行功能新增、主要功能变化和高风险修复；
- 优先使用 Apple、华为、小米等官方分阶段发布；
- 事故时暂停扩散、服务端熔断并发布更高版本前向修复。

**Content Lane**

- 只承载经过格式白名单和无执行能力验证的静态内容；
- 必须通过内容安全、许可、年龄分级、隐私与主要功能不变门禁；
- 允许自动灰度和自动回滚，但仍要留存完整审计记录。

**Exception OTA Lane**

- 技术上可支持 RN JS/Hermes，但中国生产默认 `disabled`；
- 只对明确 App、原生壳版本、渠道和变更类别发放限时策略；
- 至少需要产品、隐私、安全、法务及渠道运营批准；
- 360 目标构建不得启用；华为/iOS 目标构建仅在针对具体方案完成法务风险判断及可取得的渠道/App Review 沟通后考虑启用。内部“风险接受”不改变 Apple 或渠道规则，也不保证审核结果。

### 2. 配置与功能开关

- 把配置分为：
  - `operational`：超时、重试、容量、非用户功能参数；
  - `content`：不执行的文案/素材；
  - `product`：功能、流程、付费、权限、数据处理开关。
- 只有 `operational` 和通过内容门禁的 `content` 可自动发布；`product` 与代码同级审批。
- 禁止使用通用表达式执行器、远程 React component schema、可调用任意 Native Module 的动作 DSL 伪装成配置。

### 3. 多渠道构建与服务端策略

- 维护 `appId + platform + storefront + signer + nativeVersion` 五维身份；
- 服务端按可信身份返回策略，并将不确定安装来源降级到最严格策略；
- 不得让业务方在控制台直接绕过渠道策略；例外必须关联审批单、自动过期并可全局熔断。

### 4. Brownfield

- Brownfield 中 RN 页面由原生宿主加载，并不改变 JS/Hermes 是可执行载荷的事实；
- 宿主 App 的备案、许可、隐私和商店审核状态覆盖整个 App，不因 RN 只是局部页面而降低要求；
- 多个业务 Bundle 共享宿主时，任何一个 Bundle 改变权限、SDK 使用或数据处理，都可能影响宿主整体披露和审核。

## 十、上线前必须取得答案的开放问题

1. 公司目标 App 是否包含 360；若包含，是否接受中国生产完全关闭可执行 OTA？
2. 华为、vivo、荣耀、应用宝当前合同/控制台对 RN JS、Hermes bytecode、远程配置和自更新 APK 的具体条款是什么？荣耀已公开的应用市场 SDK/查询接口及老机型安装器说明具体覆盖哪些应用、设备和分发来源？是否有书面工单答复？
3. iOS 具体 OTA 方案是否会“引入或改变功能”，以及 App Review 是否已被完整告知并可审？
4. 产品是否实质构成 Apple 4.7 的小程序/插件容器？
5. 每个 App 的 APP 备案服务类型、签名指纹、域名、运营主体和前置审批是否与当前生产事实一致？
6. 新功能是否触发新闻、出版、教育、影视、宗教、游戏、金融、医疗等许可，或舆论/社会动员安全评估、算法备案？
7. OTA 分群、更新检测、崩溃日志和 SDK 遥测是否向境外提供个人信息或涉及重要数据？
8. 谁对“主要功能不变”“隐私事实不变”“许可仍覆盖”签字负责，审批有效期多长？
9. 渠道政策多久复核一次，规则变更时如何一键关闭所有例外 OTA？
10. 2026-11-01 前如何评估并吸收 GB/T 47469-2026；征求意见稿正式发布后如何触发规则迁移？

## 十二、研究局限

- 渠道规则是动态合同体系，部分完整规范只在登录后的开发者控制台展示；本文没有用第三方上架博客补足缺失的一手证据。

- Apple 与渠道最终审核具有事实判断和裁量；公开规则不能替代针对具体 App、具体载荷和具体业务状态的审核沟通。
- 本文只划平台设计边界，不替代每个 App 的主体、备案、许可、数据流和合同尽调。
