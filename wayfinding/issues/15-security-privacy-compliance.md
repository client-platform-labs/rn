# 安全、隐私与合规控制

## Question

针对账号、支付、精确位置、相机和用户媒体等高敏消费级 App，平台应在哪些层实施默认安全与隐私控制，并怎样允许金融/医疗等更高监管要求作为附加配置？

必须定义威胁边界、凭证与本地数据、网络与证书、日志脱敏、权限最小化、SDK/插件准入、隐私清单与同意、依赖漏洞、恶意插件、动态更新完整性、设备风险、审计、数据保留和安全例外审批。

## Answer

安全与隐私采用“**高敏消费级默认基线 + 可叠加监管配置档 + 五层落点 + 强制同意链路与例外时效**”：

1. **默认威胁边界**
   默认基线覆盖账号、支付、精确位置、相机和用户媒体。
   金融/医疗不作为默认，而以附加 `compliance_profile` 叠加更严审计、数据驻留、留存、审批和禁用能力清单。

2. **五层落点**
   - Runtime：凭证、本地加密、权限最小化、证书策略
   - Capability：权限/隐私清单、能力探测、错误模型
   - Delivery：依赖漏洞、SBOM、签名完整性
   - Control Plane：更新签名、审计、审批、Kill Switch
   - Governance：例外审批、数据保留、合规配置档

3. **凭证与本地数据**
   强制“最小保存 + 安全存储 + 明确销毁”，覆盖 token、支付相关本地态、媒体临时文件和位置缓存。

4. **网络与证书**
   默认 HTTPS；证书固定可选且必须可观测、可按 App/profile 配置。不强制全局 pinning。

5. **权限与隐私同意**
   强制四段式：`声明 → 同意 → 能力探测 → 调用`。
   未授权不得偷偷重试；权限/隐私范围变化必须阻断自动发布。

6. **SDK / 插件安全准入**
   能力包与业务插件进入生产前必须通过：
   - 依赖漏洞扫描
   - 隐私字段声明
   - 权限超额检查
   - 未签名/恶意插件阻断
   - 退役依赖阻断

7. **动态更新完整性**
   更新载荷必须端到端签名并校验企业信任根。
   更新签名通过不等于合规通过；可执行更新仍受三通道与审批约束。

8. **安全例外**
   任何绕过默认安全控制的例外都必须双人审批、有过期时间、可审计，并在到期后自动失效。

9. **审计与保留**
   权限授权结果、插件准入、更新审批、例外审批和敏感数据删除证明必须进入企业审计账本，并规定保留期。
