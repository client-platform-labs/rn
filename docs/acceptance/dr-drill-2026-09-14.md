### F1 — the distribution-service stack could not be built from a clean checkout (FIXED here)

```
docker compose -f deploy/distribution-service/docker-compose.yml up -d --build
  -> unable to prepare context: path ".../data-service" not found
```

`data-service` was a **default** service whose build context defaulted to the repo-relative
`../../data-service` — a directory that has never existed in this repository and was never
tracked in git. It is genuinely external (`~/code/data-service`, a Python/FastAPI backend for
other apps), and this repo's own docs already describe it as optional orchestration only.
Because it was a default service, both the command documented at the top of that very file and
the repo's own gate `scripts/verify-distribution-compose.mjs` were unrunnable on a clean checkout.

**Fix**: put it behind a Compose **profile** (`--profile data-service` to opt in) and point the
context default at the real location. Also fixed two host mounts that used a literal `~`
(Compose does not expand it, so it created a directory literally named `~`).
Verified: `docker compose config --services` → `distribution` only; with the profile → both;
the repo gate now passes (above).

### F2 — the running image is stale relative to the source, and nothing detects it

`client-platform/cp:local` was built **2026-09-10**; the source tree here is **2026-09-14**.
Consequence, measured: `/v1/crl` from that image returns **only** `{"schemaVersion":1,"revoked":[...]}`
— **no `payload`, no `seal`** — i.e. it predates the ADR-024 CRL-signing work, so the deployed CP
serves a CRL shape that no current device can trust. Rebuilding from the current source
(`docker build -f deploy/Dockerfile -t client-platform/cp:drill .`, rc=0) yields
`{"schemaVersion":1,"revoked":[...],"payload":"…","seal":"pem:ed25519:…"}`.

Nothing in the stack reports image↔source drift; `deploy.sh` reuses an existing image unless
`CP_REGISTRY` is set. **This is the ADR-009 "contract vs implementation" family at the deployment layer.**

### F3 — in cert mode one key cannot serve both the CRL and the releases (PROVEN)

`serve.ts:636` warns, in its own words: *"IMPORTANT (ADR-024 cert mode): the CRL must be signed
with the RCA private key baked into the APK (--rca-pubkey-hex); signing with the leaf key instead
makes devices reject every CRL."* But only **one** key input exists
(`RN_DELIVERY_SIGN_KEY_PEM` / `RN_DELIVERY_SIGN_KEY_FILE`) and `buildCrlDoc` uses the same
`signCanonicalPayload` as candidate sealing — there is **no CRL-specific key variable**.

Measured with the platform's own verifier `verifyRevocationSealAny(seal, payload, [key])`,
against the **RCA public key a device would bake**:

| Container signing key | seal verifies vs the LEAF | seal verifies vs the RCA (device) |
|---|---|---|
| `dr-drill.key` (leaf — the documented release-signing key) | `true` | **`false`** → device rejects every CRL |
| `dr-drill.rca.key` (RCA) | — | `true` (but then release seals are RCA-signed, which the device verifies under the **leaf** chain) |

So following the documented configuration produces a CRL that every device rejects; and the
configuration that produces an acceptable CRL breaks release verification. **A single instance
cannot satisfy both.** (Reported, not fixed: `packages/**` is another lane's scope.)

### F4 — ADR-014's cold rebuild restores the DATA but not the TRUST (PROVEN)

The drill (`deploy/distribution-service/dr-drill.sh`, committed here) does a **true** cold rebuild:
it destroys the project **and all platform key material**, keeping only the offsite age identity
(as ADR-014/F05 intends), then restores from the archive alone.

```
BEFORE rebuild — device (bakes RCA) accepts CRL?  true
AFTER  rebuild — device (bakes RCA) accepts CRL?  false
```

* Data: **recovered** — `staging=1` before and after; `registry.json` + `artifacts.tar` restored,
  manifest sha256 verified, `failures: []`.
* Trust: **not recovered** — the archive captured a single secret file (`delivery-sign.pem`,
  the file named by `RN_DELIVERY_SIGN_KEY_FILE`) while cert-mode `ship keygen` had produced
  **6** artifacts (`*.key`, `*.leaf.crt`, `*.rca.key`, `*.rca.crt`, `*.csr`, `*.srl`).
  After the rebuild the CP signs the CRL with the leaf ⇒ **the device rejects it** ⇒ and because
  the boot path is fail-closed, **OTA updates stay blocked after a disaster recovery.**

So ADR-014's promise ("十几分钟重建后恢复服务") holds for the *service and its data*, and fails for
*the service's ability to serve devices* in the current cert-mode default.

### F5 — an exported security verifier throws instead of failing closed

`verifyRevocationSealAny(undefined, payload, keys)` →
`TypeError: Cannot read properties of undefined (reading 'startsWith')` from
`packages/core/src/ed25519-verify.ts:95`, because `seal.slice(...)` sits **outside** the try/catch.
The function's contract is to return a boolean (fail closed). Today's device path guards with a
`typeof body.seal !== "string"` check first, so it is latent — but any other caller passing a
malformed CRL gets a crash rather than `false`. (Reported, not fixed: `packages/**`.)

### F6 — hygiene: the compose smoke writes a token-bearing file that is not gitignored

`scripts/verify-distribution-compose.mjs` writes `deploy/distribution-service/.env.verify`
containing a bearer token, and it is **not** covered by `.gitignore` (checked). I removed the file
after each run; a repo-level ignore entry (or writing it under the OS temp dir) would be safer.

## 2. How to reproduce

```bash
# S7: the repo's own compose gate (self-cleaning)
node scripts/verify-distribution-compose.mjs

# build the CP image from the CURRENT source (the running :local tag is stale — see F2)
docker build -f deploy/Dockerfile -t client-platform/cp:drill .

# S8: the cold-rebuild drill (destroys only its own /tmp root + its own containers)
bash deploy/distribution-service/dr-drill.sh "$PWD"
```
