## leg B 为什么能过（本次修复的过程发现）

原 SKIP 根因有两层：
1. **共享 CP 容器未配 cert 模式**（`/v1/crl` seal=null）→ 设备 fail-closed 拒载。本次用隔离本地 CP（leaf 签名 + cert_chain）规避，未动共享容器。
2. **更深一层**：DUT 增量 Gradle 构建把 **P1 前的 JS bundle** 嵌进了 APK（Metro bundle 任务 UP-TO-DATE）——设备端只做 legacy 验签，leaf 签 CRL 必拒（实测 logcat `CRL seal invalid`）。强制 `:app:createBundleReleaseJsAndAssets --rerun-tasks` 重跑后 APK 含 P1 标记（`CRL chain invalid`），B1/B2 即过。

**教训（footgun）**：增量构建可嵌入陈旧 shell-core JS。e2e 验收应强制重跑 bundle 或校验 APK 内的 P1 标记。

## leg A 为什么失败（真实发现，已开票）

- 注入确认 4/4（每次启动在计数递增后、完成前被杀，阈值 DEFAULT_CRASH_LOOP_MAX=3）。
- 手动隔离复现：反代到死端口，6 次强制失败 → 第 7 次仍无回滚。
- DUT 内嵌 JS（release-boot/crash-loop）与仓里一致；OtaModule.kt 的 `recordStartupFailure`/`resetStartupFailures` 为真持久化实现（SharedPreferences）。
- 结论：**崩溃环计数器在这台设备上不累计**（或回滚守卫未达），与代码不符——需单独调查（原生 prefs 持久化 / 壳 boot 路径 / RN 桥返回值）。
- 影响：若为代码缺陷，设备崩溃环**不会自动回滚**，是安全验收级问题；morning sweep 的 leg A PASS 与其矛盾，需复核当时的 DUT 构建。
